# PiPER control state machines

This inventory covers the PiPER plugin, managed controller and gripper services, native controller, and web clients. It includes transitions encoded in flags, request lifetimes, telemetry comparisons, and timers as well as explicit enums. The physical firmware and Lucky Engine runtime appear here at their observable protocol boundaries.

**P0** marks motion authority, power, and stopping. **P1** marks evidence and presentation used by those decisions. **P2** marks workflows that can evolve separately. Each row names the owner and its transition evidence. Keep a transport acknowledgement, a measured outcome, and a UI label distinct.

The normative target for every machine is section 3 of [target-architecture.md](target-architecture.md). This document records what the code does now. Where the two differ, the index below says so in its last column.

## Kind

The **Kind** column states how the code stores a machine's state. It describes the storage, not the quality of the behaviour.

| Kind | Meaning |
| --- | --- |
| **Explicit** | One enum, or one tagged record type, is the single stored state. Its transitions are written in one place. Payload fields may sit next to it, but they cannot encode a different state. |
| **Record** | One immutable record held in one field and replaced whole. Its states are derived from which record fields are set. No enum names them. |
| **Derived** | No stored state value. The state is computed from several fields. The legal combinations are documented next to the fields and asserted (`assert` in C). The C# plugin and camera tool check them at runtime instead of with `Debug.Assert`, which Release builds drop: a broken combination refuses the action or clears motion permission, and tells the operator. |
| **Partial** | A state enum exists, but other fields that encode the same machine are still stored separately. |
| **Mixed** | A behaviour that spans several machines, some explicit and some not. Used only in the behaviour tables below. |
| **Implicit** | State lives in flags, timers, tasks or text. Nothing names it. |

#### Persisted recovery record (B10)

Each device's record in `control-state.json` now carries explicit fields. Recovery eligibility reads `state` and `kind`, never the reason text.

| Field | Values | Written by |
| --- | --- | --- |
| `state` | `clear`, `latched`, `reset_pending` | `latch()`, `clear_latch()`; old records get it once from `blocked`/`reset_pending` in `record_normalize()` |
| `kind` | `intent`, `stop`, `obstruction`, `power`, `reset`; empty when `clear` | `latch()`; old records get it from `legacy_kind()` |
| `stop_event.kind` | `stop`, `obstruction` | `lane_stop()`; old events get it from the reason prefix in `record_normalize()` |
| `blocked`, `reset_pending` | booleans | still written beside `state`, so an older build reading the file stays blocked |
| `kind_reason` | the `reason` text `kind` was set for | `latch()` and `clear_latch()` write it with `reason`; a mismatch means an older build rewrote `reason`, so `record_normalize()` derives `kind` again |
| `stop_event_active` | boolean | `lane_stop()` sets it; `clear_latch()` clears it. It implies a latch: `record_normalize()` turns a `clear` record that carries it into `latched` |

`teaching_return_guard()` (`src/controller.c:570`) admits `recover-at-pose` only when `state` is `latched`, `stop_event_active` is set, `kind` and `stop_event.kind` are both `obstruction`, and the incident is otherwise recoverable. `relinquish_to_teaching()` (`:622`) clears only a lane's own `kind == intent` latch, and only without active STOP evidence or a pending reset.

The state frame does not project `state` or `kind` directly. Each `devices[]` entry exposes `recovery_required`, `reset_pending`, `stop_reason`, `stop_event` (including `stop_event.kind`), `last_fault` and `last_cleanup_error`.

#### Agent device identity is checked twice on purpose

`PikaSerialDevices.ResolveLinux()` already resolves the configured device through the sysfs inventory, which accepts only a CH340K (`1a86:7522`). The agent then walks sysfs again from the resolved tty (`/sys/class/tty/<tty>/device` up to the USB node's `idVendor`/`idProduct`) before it takes the device lease and opens the port (`AgentProgram.Run` in `managed/Piper.Pika.Agent/Program.cs`). The second walk is a deliberate safety double-check, not leftover duplication: it reads the identity of the exact node the agent is about to open, so a tty that was re-enumerated to another adapter between inventory and open is refused. Keep it when refactoring the resolver.

## Web clients

The web arm dashboard mirrors the selected lane, readiness, and errors. It owns its client heartbeat, request lifetime, and unload handling. Those timers do not replace native admission. Each module keeps one `phase` value:

- **Lease** (Web‑A): `lease = {phase, request_id}` in `web/app.js`, phases `none`, `pending`, `leased` and `stopping`, changed only by `setLease()`.
- **Approval** (Web‑B): `approval = {phase, prompt}` in `web/app.js`, phases `unapproved`, `prompting` and `approved`, changed only by `setApproval()`. It covers motion commands only and states the `standalone` and `clear` flags it sends. Power and recovery actions take their flags from the `attestations` table, one operator confirmation per click; nothing adds a flag without the dialog that states it.
- **Reset attestation** (plugin, B1): `ResetCompletionPrompt` in `ResetCompletionConfirmation.cs`, pinned to the robot scope and permission epoch. `verify-reset` carries `reset_completed` only from `ConfirmResetCompletion()`, after the operator answers "Has the controller reset or power cycle completed?" with Confirm; Cancel sends nothing, and `Command()` refuses `verify-reset` without it. Confirm also sends nothing unless fresh feedback still reports `reset_pending` for that robot. Recovery to zero and supported STOP recovery stop at that question instead of verifying a pending reset.
- **Pika port** (Web‑C): `session.phase` in `web/pika.mjs`, phases `disconnected`, `connecting`, `read-only`, `armed` and `moving`, changed only by `setPhase()` against a `transitions` table. The same `session` record holds the operation (`busy`), the in-flight Host request (`request`) and the telemetry watch.
- **Operator STOP**: `stopAll()` in `web/app.js`. It posts `{owner}` and nothing else, so no client belief can scope or void it, and dispatches `piper-stop`, on which `pika.mjs` posts its own disable.

The browser Pika UI is a client of the Host's Pika routes through `PikaClient` (`web/pika_remote.mjs`): it projects the agent's telemetry and sends connect, enable, disable, target, heartbeat and disconnect requests. The Linux agent is the only jaw authority (target-architecture Q5); the direct Web Serial path is gone, and on the native daemon, which has no Pika routes, the panel is unavailable.

The native controller and Pika agent retain their causal checks and local watchdogs. A received command, a successful wire write, and fresh measured acknowledgement are three distinct events. The offline fixtures verify the software transitions above. Physical Follow, recovery, camera latency and teardown still need validation on the workstation.
