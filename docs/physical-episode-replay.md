# Physical episode replay

The plugin's **Recording → Review a simulation episode for physical replay** page loads a finished project export. It displays the saved tube start, object dimensions, goal, first six joint angles and Pika opening. The operator can confirm the physical tube placement and compare fresh robot measurements against the first pose. Recheck requires the selected robot in an Edit scene and validates the recorded joint targets against fresh reported joint ranges, speeds and per-joint acceleration caps. The controller's `acceleration_fresh` flag must be true for each joint; `max_acceleration_rad_s2` is converted to degrees/s². Missing, stale or invalid acceleration reports block review/planning; no default cap is substituted.

The page currently sends no movement or motor-power commands. **Start physical replay** remains disabled until the backend supports coordinated arm and Pika playback. Navigating to robot controls remains a separate action; loading a trajectory never homes the arm or generates an approach move.

## Missed grasps during live Follow simulation

The live ordered follower treats an expected missed grasp as an unsuccessful trial, rather than a controller fault. If healthy, stationary real jaws settle at the closing command without confirming the simulated contact, the plugin reports **Grasp not confirmed · continuing the cycle to home**. It keeps the original ordered carry, lower, release, withdraw and home path; it does not generate a shortcut home or open the jaws unexpectedly in midair. Aperture alone does not prove that an object was grasped.

The project marks expected simulated grasp failures with `missed-grasp-<phase>:<ordinal>` and finishes with `missed-grasp-finish` only after its ordered home. The follower retains these commands through physical completion. A settled, unchanged real jaw reference remains authoritative when a known missed trial leaves simulation and physical contact different; actual jaw drift still has its existing 2 mm bound. Other source failures remain hard failures.

If previously qualified contact is lost while carrying, the plugin also checks for closure toward the exact unchanged closing command. Within 250 ms, the jaws must settle between 1 mm below and 2 mm above that command for 100 ms across two fresh feedback samples, even if the arm is still moving. This band means contact is unconfirmed; it does not prove that the jaws are empty. The trial is marked unsuccessful and continues along the same path. No new jaw command is sent. Opening or reversal beyond 2 mm, an overshot endpoint, a changed command, stale feedback, or failure to settle within that window still stops following. The same band handles an initial settled close; it leaves no gap between commanded arrival and the strictly greater than 2 mm contact-candidate threshold.

After the final home frame, fresh feedback must confirm stationary joints within 0.25° of zero and arrival at an explicitly completed opening reference. Only then does the plugin end following with normal scoped holds and an unsuccessful-trial message. It sends no success acknowledgement and permits no automatic next episode. Driver or CAN faults, lost ownership, stale feedback, joint tracking errors and unexpected physical jaw changes still stop following immediately; missed-grasp handling never resets or bypasses those guards.

## Export contract

`lucky.piper.joint-trajectory` version 1 contains measured simulation observations and is **review-only**. The physical planner rejects it. Version 2 adds mandatory `commandedJointDegrees`, `commandedGripperOpeningMm` and `commandSource` to every sample. Physical planning uses those position-controller targets; it never substitutes measured `jointDegrees`/`gripperOpeningMm` for actions. Both sets of joint values have exactly six entries in physical J1–J6 order and degrees. Gripper values are the gap between the jaws in millimetres, not finger slide or motor angles.

Version 2 explicitly marks commands as postphysics Validation samples held until the next command sample. Intermediate internal control updates are not represented. Actual allowed Pika opening (`gripperMaximumOpeningMm`, 90 mm) is separate from its geometric zero-slide gap (`gripperReferenceGapMm`, approximately 94.044 mm). The exporter records the pinned authored model hash and its position-actuator/mapping checks. This is audit provenance; the runtime API does not independently expose the full actuator-law type.

Samples start at zero seconds and increase strictly. `nominalCaptureHz` records the producer's intended capture rate; actual sample timestamps remain authoritative. Sync indices may repeat because Validation capture can run faster than cross-runner synchronization. The reader bounds file size, sample count and duration, validates the desk-relative/world tube placement, and rejects duplicate/unknown fields, invalid captures, missing v2 commands and alternate command conventions.

The initial tube LEFT/BACK distances, yaw, world pose, dimensions and mass provenance are retained with the seed, project episode ordinal, outcome and optional operator-supplied native recording label. Full native MuJoCo qpos is retained only as audit evidence. The planner never interprets that array as hardware targets. A native recording label/ordinal does not independently prove that a native dataset passed finalization.

`EpisodeReplayPlanner` validates physical limits supplied by its caller. It compares the real starting arm against the first **measured** simulation pose, and separately checks the first **commanded** target against that source pose to expose an initial jump. It never clips positions and rejects excessive inter-sample command rates unless uniform time scaling is explicitly requested. Scaled timing is recorded in the plan; zero-order-hold command semantics remain explicit. A future executor must recheck controller mode, ownership, faults, connection generation and fresh measurements immediately before starting; the position plan alone does not authorize execution.

Joint reference velocities use each actual sample interval. Sampled reference acceleration is the change between adjacent interval velocities divided by the time between their midpoints. Uniform timing must satisfy both speed ratios and the square root of each acceleration ratio; gripper speed can require a larger factor. For example, a 653.525°/s² reference peak against a reported 0.5 rad/s² cap (28.648°/s²) needs at least 4.7763× timing from acceleration alone. This is a finite-difference reference check, **not a guarantee of physical acceleration at instantaneous zero-order-hold transitions**. Endpoint transients, contact forces and unrecorded internal control updates are not reconstructed. With only two samples there is no interior acceleration estimate. Targets are never smoothed or replaced, and time scaling still needs explicit consent. A start recheck rejects newly stale or reduced caps.

## Backend foundations available

These transport foundations do **not** enable physical episode replay. Pika state explicitly reports `physical_replay_available: false` and `verified_maximum_opening_speed_mm_s: null`. There is no replay executor or automatic motion on loading a recording.

The existing one-shot `/api/pika/position` behavior is unchanged. For a separately authorized, enabled Pika agent, the HTTP and gRPC control routes now also accept:

- `/api/pika/follow-start` with the existing `owner`. Fresh enabled feedback (less than 250 ms old), a live owner and no outstanding one-shot position are required. Its acknowledgement returns a new opaque `follow_session`; start itself sends no position or enable command.
- `/api/pika/follow-update` with `owner`, `follow_session`, a positive strictly increasing integer `sequence`, and `opening_mm` in 0–90 mm. It replaces one pending target; it does not queue a trajectory or clamp values. Old/foreign/expired sessions and duplicate/out-of-order updates are rejected. Acknowledgement means accepted, not reached.
- `/api/pika/hold` with `owner`. It cancels pending following and one-shot targets **before** attempting one position command at the latest fresh enabled measured opening. It preserves the enabled position servo rather than disabling the gripper. Missing feedback or a write failure reports failure; successful command acknowledgement does not independently verify holding torque. Resume requires a new follow session or a separate ordinary position command.
- `/api/stop/coordinated` with `owner` and any existing arm stop identity fields (`device_id`, `generation`, `request_id`). It attempts the existing guarded arm `/api/stop` and Pika hold independently. HTTP and gRPC return `{ok, arm: {ok, message}, pika: {ok, message}}`, with 200 only when both attempts acknowledge success, otherwise 409. Each attempt has a three-second reporting deadline; timeout means unverified state, and an uninterruptible native call can finish later. Request disconnection does not skip the other stop. No automatic reset or resume occurs. A stale arm generation still stops that arm and is reported as a failed (409) arm result naming the scope mismatch; a mismatched Pika owner is reported for that channel, not bypassed.

The serial agent uses a bounded 32-line input buffer, processes a bounded batch per tick, and retains only one current following target. Following writes use a configurable minimum command period (`--pika-command-period-ms` on the host, 30–250 ms, default 30 ms). State exposes `follow_minimum_command_period_s` and `follow_maximum_command_hz`. These describe command traffic and **are not physical jaw speed limits**; they do not certify replay timing or rate-limit the gripper's internal servo velocity. The existing one-shot resend cadence remains separate.

Following requires another target within 250 ms. A missed input deadline retires the session and, with fresh enabled feedback, holds the measured opening once. Explicit/deadline hold does not automatically disable on client-heartbeat expiry; explicit disable/disconnect, agent shutdown and transport failure remain separate lifecycle events. Loss of fresh enabled feedback retires following and reports an unverified hold. Hardware behavior after missing feedback or a failed write has not been qualified for physical replay.

Fake-writer tests cover latest-target replacement, configured command cadence, session changes, old/duplicate targets, malformed opening limits, input expiry, measured hold, unavailable feedback, failed writes, and both stop outcomes when either channel throws, cancels or blocks. These tests open no device.

## Backend follow-up: coordinated replay session

The existing arm follow API accepts sequenced target updates and has a 250 ms input deadline. The new Pika follow and coordinated stop routes above remove the single-active-target and skipped-second-stop transport blockers. Pika still exposes no verified maximum jaw-opening rate. The existing arm-only `/api/stop` route and plugin stop UI are unchanged; a future coordinated executor must use the coordinated route and retain its per-channel outcomes.

Before enabling replay:

- Add one replay session identity binding the backend token, robot profile, CAN generation and Pika assignment. Reject stale or out-of-order updates on either channel.
- Supply a verified physical opening-rate limit. Preserve jaw-opening units through the planner and convert to motor angle only at the existing Pika boundary; the configured command cadence is not this limit.
- Validate the combined schedule against the configured Pika command period too. Live following deliberately coalesces a faster producer into its latest target; exact episode replay must not silently drop distinct exported command samples. Reject an unrepresentable schedule or explicitly time-scale the whole arm/gripper plan (for example, distinct 50 Hz Pika targets need at least1.5× timing at a30 ms wire period). Repeated identical targets can retain their existing hold semantics without inventing intermediate actions.
- Bind the existing Pika session and coordinated stop foundation to the combined replay identity and enforce cancellation across both channel lifetimes. The current Pika session is scoped to its serial agent/owner, not yet to a CAN generation or robot profile.
- Execute the exported zero-order-hold command schedule against a monotonic clock; do not invent intermediate command samples. End, fault, stale feedback, missed deadlines, teaching takeover, profile/scene changes and lease loss must terminate the session. No queued target may survive a new session.
- Cover start-pose rejection, explicit time scaling, arm/gripper scheduling, end-of-file, cancellation and partial-stop failures with fake transports before a physical replay test.

Camera previews are separate from dataset recording. This replay preparation page does not claim synchronized real camera/joint capture or policy-training readiness.
